# Pre-computed benchmark results

These CSVs are the canonical benchmark numbers for the RoSE pickers (the
accompanying paper is in preparation). They cover nine pickers: the three
checkpoints in `../models/` — **EQT-RoSE** and **PhaseNet-RoSE** (fine-tuned on
the RoSE training split from INSTANCE init) and **RED-PAN-60s** (the published
RED-PAN 60 s checkpoint `REDPAN_60s_240107`, trained on Taiwan + STEAD +
INSTANCE plus Romanian (RO) events with the same development and test split
as RoSE — see `../models/README.md`) — plus six
off-the-shelf SeisBench baselines (EQT / PhaseNet × `instance` / `ethz` / `stead`).

They are regenerated by **`bash phase_picking/benchmark/regenerate_results.sh`** — which runs
stage (a) `phase_picking/benchmark/run_inference.py` then stage (b)
`phase_picking/benchmark/build_leaderboard.py --update-results` (needs the RoSE + STEAD test
datasets — see `../benchmark/README.md`). For the RoSE pool, false positives are
counted on dedicated STEAD *noise* traces only (RoSE event labels are
incomplete), with unmatched-on-event picks kept as a separate diagnostic column.
To rebuild *without* overwriting these files, run the two stages directly and
drop `--update-results` from the second — it then writes only under
`benchmark/config.json`'s `eval_dir` (default `eval/`, gitignored).

## RoSE pool (32 374 events + 23 526 STEAD noise)

* `rose_picking.csv`        — phase-pick TP/FP/FN, precision, recall, F1, MAE,
  median, std, MAD, RMSE, IQR per phase × threshold per model.
  *FP convention*: counted on STEAD-noise traces only (RoSE labels are
  incomplete; unlabelled aftershocks would otherwise appear as FP).
* `rose_detection.csv`      — trace-level event-vs-noise detection T1
  (precision/recall/F1, Matthews correlation, AUC) plus detection-box IoU
  + start-time / end-time MAE for models with detection heads.
* `rose_residual_stats.csv` — residual statistics at threshold 0.30.
* `rose_picking_manual_only.csv` — the picking metrics at threshold 0.30 on
  the analysts' picks alone (no RED-PAN-60s repicks), from
  `../benchmark/build_subset_tables.py`.

## STEAD pool (103 040 events + 23 526 noise)

* `stead_picking.csv`     — same columns as `rose_picking.csv`, but FP follows
  the canonical pick-benchmark convention (events + noise pooled) because
  STEAD labels are clean.
* `stead_detection.csv`   — trace-level T1 + detection-box quality on STEAD.

## RoSE pool with RoSE noise (32 374 events + 13 317 RoSE noise windows)

* `rose_noise_false_picks.csv`    — per model × threshold, the noise traces with
  a pick and the picks per hour, RoSE noise next to STEAD noise.
* `rose_picking_rose_noise.csv`   — `rose_picking.csv` with the false positives
  counted on the RoSE test-split noise windows instead of STEAD noise.
* `rose_detection_rose_noise.csv` — the same for `rose_detection.csv`.

Built by `phase_picking/benchmark/build_rose_noise_benchmark.py`; see the
RoSE-noise leaderboard below.

## Threshold sweep

Each CSV has rows for every (model, threshold) combination over the
six-point sweep `{0.05, 0.10, 0.20, 0.30, 0.50, 0.70}`. The tables below are at
**threshold 0.30**; the bold rows are the three checkpoints in `../models/`,
the rest are off-the-shelf SeisBench baselines for context.

**149 test traces cannot be picked, and 328 more are picked less well.** In
149 test traces the last sample of one to three components is +inf or -inf,
and in 328 more it is finite but far too large. All are BH traces resampled
from 20 or 50 Hz with ObsPy's `Trace.interpolate(100)`, whose default method
can read one value past the end of its input. The cause, the counts and a
repair function are in
[`docs/SEISBENCH_FORMAT.md`](../../docs/SEISBENCH_FORMAT.md#known-issues-in-the-earthquake-traces).
The whole dataset has 928 traces with an infinite end sample (645 train, 134
val, 149 test) and 2,139 with a finite one that is too large; the noise set
has none. Any normalisation turns a trace with an infinite sample into NaN, so
every model misses every label on them: 122 of the 27 309 traces with both
labels (60 P and 70 S labels manual), so recall cannot exceed 0.996 for either
phase and 0.9955 for detection, and the tables above count them as misses for
every model; EQT-RoSE misses only one other trace in detection. On the 328
traces with a large finite end sample, the models find 18 to 44 % fewer labels
than on clean traces. Together, the 477 traces lower recall in
`rose_picking.csv` at threshold 0.30 by 0.003 to 0.006 for every model, and
they do not change the order of the models. A corrected dataset version would
change only one sample in each affected component.

also be counted on Romanian noise. Here they are counted on the middle 60 s of

then `build_rose_noise_benchmark.py`); the event side (TP, FN) is that of the

Every model picks less often on this RoSE noise than on STEAD noise, so
precision and F1 rise, and the order of the models barely changes. Three
things limit what this shows:

* The windows are not a neutral sample of Romanian noise. A window was kept
  only if four pickers found no P or S peak above 0.1 in it: RED-PAN 60 s (the
  weights of RED-PAN-60s here), PhaseNet+, and the original EQTransformer and
  PhaseNet weights (`docs/SEISBENCH_FORMAT.md`, "Noise chunks"). This rule
  removed 37 061 of the 53 900 candidate test windows (69%). Models that behave
  like these four, RED-PAN-60s above all, pick less on this set by
  construction, so its false-positive rates are optimistic, most of all for
  RED-PAN-60s. The leaderboard with STEAD noise above remains the main one.
* "Noise" means no detected local arrival. When the nine models ran on the
  whole 100-s windows, three or more of them picked within 1 s of each other
  inside 20–80 s in 50 windows, which probably hold small real events.
* RED-PAN-60s was trained with the same development and test split as RoSE,
  so these test-split windows belong to events outside its training set.

## RED-PAN-60s on records longer than 60 s

RED-PAN-60s reads 60-s windows. For a longer record, `rose.redpan_inference`
pads both ends with spectrum-matched noise and averages sliding windows over
it. Up to toolkit v0.4.0 both pads were matched to the start of the record
and the noise generator was not seeded, so each run gave slightly different
probabilities; where the end of the record met a pad that did not match it —
coda, or the zero tail of a STEAD noise array — the model saw an onset and
made a spurious P pick in the last second. The wrapper now matches each pad to
its own end of the record and seeds the noise on every call. On random samples
of the test sets, at threshold 0.30:

| sample | records with a pick, before → after | picks in the last second, before → after |
|---|--:|--:|
| 1 000 RoSE noise windows (100 s) | 76 → 1 | 74 → 0 |
| 500 STEAD noise traces (270 s) | 21 → 9 | 12 → 0 |
| 400 RoSE event traces (90–178 s) | — | 23 → 0 |
| 300 STEAD event traces (270 s) | — | 0 → 0 |

On the 400 RoSE event traces the probability near the labelled picks changed
by 0.002 on average (at most 0.05); at 0.30 one labelled pick was gained and
one lost. On the 300 STEAD event traces nothing changed: the pads reach only
the first and last 60 s of a record, and the STEAD labels lie between them (P
at 90 s, S at 90–124 s in this sample).

The RoSE-pool rows above were recomputed with the fixed wrapper on
2026-10-29 (all nine models; the eight PyTorch models reproduce their earlier
rows within four picks). For RED-PAN-60s at threshold 0.30 the P picks on the
23 526 STEAD noise traces fell from 551 to 295 and the noise traces with any
pick from 713 to 474, so P precision rose from 0.974 to 0.986 and P F1 from
0.822 to 0.826; S F1 stayed at 0.827. In event-vs-noise detection the false
positives fell from 713 to 474 and the true positives from 24 257 to 24 045,
so det F1 stayed at 0.928 and MCC rose from 0.856 to 0.859. On the event
traces the matched picks moved by a few (P 20 544 to 20 541, S 21 958 to
21 965) and the unmatched picks fell from 8 017 to 5 952 (P) and from 6 744
to 4 840 (S): the end picks are gone. The RoSE-noise leaderboard was never
affected, because a 60-s window goes to the model directly, without padding.
On the STEAD pool the same rerun left the event side unchanged (at 0.30,
P 100 550 and S 101 029 matched picks, as published) and removed the end
picks on the STEAD noise traces: the P false picks fell from 3 348 to 2 809,
the S false picks from 2 039 to 2 035 and the noise traces with any pick to
474, as in the RoSE pool, so P precision rose from 0.968 to 0.973, P F1 from
0.972 to 0.974, T1 F1 from 0.996 to 0.997 and T1 MCC from 0.977 to 0.983.
The eight PyTorch rows of the STEAD tables are the published ones; the fix
does not concern them.

## EQT-RoSE — Münchmeyer-2022 / Section-3 protocol

Produced by `phase_picking/benchmark/eval_eqt_rose.py --ckpt ../models/eqt_rose/eqt_rose.pt
--rose-dir <rose>` on the full 32 374-trace RoSE test split (a *different*
evaluation protocol from the pipeline above — SeisBench fixed-window generator,
picks recovered from the Gaussian label channels, and a synthesised post-event
**coda** window as the T1 negative since RoSE has no dedicated noise traces):

| Task | Metric | EQT-RoSE |
|---|---|--:|
| T1 — event detection | F1 / AUC | 0.928 / 0.57 ⚠️ |
| T2 — phase identification (P vs S) | MCC (n = 34 140) | 0.730 |
| T3 — onset time, **P** | MAE / RMSE / IQR (n = 11 918) | 0.072 s / 0.111 s / 0.08 s |
| T3 — onset time, **S** | MAE / RMSE / IQR (n = 16 984) | 0.162 s / 0.209 s / 0.25 s |

⚠️ The T1 AUC (~0.57) is artificially depressed because EQT's training label
marks samples up to `S + 1.4·(S−P)` as event-positive, so the first half of
each coda-window "negative" is still in-event by EQT's own definition — treat
T1 here as advisory only (use `--skip-t1` to suppress). The pipeline's
STEAD-noise-based T1 for EQT-RoSE is F1 0.973 / MCC 0.942 (`rose_detection.csv`);
T2/T3 above are robust.

## Regenerating

`bash phase_picking/benchmark/regenerate_results.sh` rebuilds the five
leaderboard CSVs (see `../benchmark/README.md`). It runs `phase_picking/benchmark/run_inference.py` (stage a —
per-model inference → `eval/`) then `phase_picking/benchmark/build_leaderboard.py
--update-results` (stage b — aggregates → these CSVs). `build_leaderboard.py`
internally drives `build_rose_final_benchmark.py` / `build_rose_residual_stats.py`
/ `build_stead_full_benchmark.py`, each of which also prints its threshold-0.30
leaderboard table to stdout (`python phase_picking/benchmark/build_leaderboard.py --threshold 0.5`
to display a different one — the CSVs always carry the full sweep). The three
RoSE-noise CSVs come from the standalone RoSE-noise leg in the same README.
